## 正向验收

夹具在 `compiler/graph/testdata/init`：`main.ts` 先导入 `b.ts`、再导入 `a.ts`，两者都依赖 `shared.ts`。

```text
$ ./bin/tynel dump init --root compiler/graph/testdata/init main.ts
{
  "order": ["…/shared.ts", "…/b.ts", "…/a.ts", "…/main.ts"],
  "prints": [
    {"module": "…/shared.ts", "value": "1"},
    {"module": "…/b.ts", "value": "3"},
    {"module": "…/a.ts", "value": "2"},
    {"module": "…/main.ts", "value": "4"}
  ]
}
```

对应打印顺序：

```text
1
3
2
4
```

- `shared.ts` 从两条路径到达，只执行一次，只打印一次。
- `b.ts` 在 `a.ts` 前，因为 `main.ts` 先写 `b` 的导入；顺序不是模块名字典序。
- 把 `main.ts` 的两行导入对调，`a` 会先于 `b`，打印顺序变为 `1 2 3 4`。

### 纯类型依赖不执行

`type-main.ts` 只 `import type { T } from "./types.ts"`；`types.ts` 里有 `console.log(9)`。

```text
$ ./bin/tynel dump init --root compiler/graph/testdata/init type-main.ts
{
  "order": ["…/type-main.ts"],
  "typeEdges": [{"from": "…/type-main.ts", "to": "…/types.ts", "typeOnly": true}],
  "prints": [{"module": "…/type-main.ts", "value": "5"}]
}
```

`types.ts` 不进入执行顺序，`9` 不会打印；类型边仍保留，检查阶段仍会读取它。

## 顶层 const 的存储与读取规则

- 每个进入 `order` 的模块执行一次初始化。
- 顶层 `const` 在所属模块初始化时求值并写入该模块存储。
- 导入的顶层 `const` 通过 `(Module, ID)` 读取目标存储，不复制值。
- 函数读取模块级 `const` 仍报 `module.captured-variable`；本轮不实现闭包或隐式环境。
- 类型别名没有存储，不产生初始化动作。

05.05 只输出顺序和规则；把这些初始化语句合并进一个 NIR 入口由 05.06 完成。`prints` 只识别字面量 `console.log`，用于核对顺序，不是执行器。

## 交付后的副作用导入初始化修复（2026-11-11）

本节记录副作用导入被接受、目标模块却不执行的一次运行时语义修复，执行时间是 2026-11-11 00:12 CST，代码基于提交 `7855d58` 的工作树。环境：Mac mini（Apple M4，arm64）、macOS 26.6.2、隔离 go1.27.3、前端 typescript/v7.0.2。上文「本轮边界」中把默认导入、命名空间导入一律写成拒绝的说法，自本节起按实际行为收窄。

修复前的断裂链：`Session.Imports()` 和依赖图都能发现 `import "./register.ts"`；适配层 `declareImport()` 在没有 `ImportClause` 时提前返回，`Facts.Imports` 没有记录；能力检查对 `ImportDeclaration` 直接放行；`modules.Plan()` 只按 `Facts.Imports` 排初始化顺序；`loadMerged()` 只降低 `plan.Order` 里的模块。结果是依赖文件被发现、读取和检查，却没有执行，程序正常编译并静默丢失副作用。

基线复现（临时夹具，不提交）：

```typescript
// main.ts
import "./register.ts";

console.log(1);
```

```typescript
// register.ts
console.log(2);
```

```zsh
# 修复前：只输出 1，退出 0；register.ts 没有进入初始化顺序。
./bin/tynel run --root /tmp/tynel-sideeffect.… main.ts
./bin/tynel dump init --root /tmp/tynel-sideeffect.… main.ts
```

`dump init` 的 `order` 只有 `main.ts`，`valueEdges` 为 `null`，而 `dump graph` 已经包含 `main.ts -> register.ts` 的值边。

修复把「模块依赖边」和「具名导入绑定」分开建模：

- `frontend.Facts` 新增 `dependencies`：每条导入声明一条边，带目标模块、`typeOnly` 和位置。`imports` 只保留命名导入的本地绑定。
- 适配层对每条 `ImportDeclaration` 记录依赖边；副作用导入、默认导入和命名空间导入没有绑定，但仍有边。
- `modules.Plan()` 只按 `dependencies` 排顺序；`typeOnly` 为真的边只记入 `TypeEdges`，不触发执行。
- `Facts.Validate()` 增加 `facts.bad-dependency`；宿主在入口只有副作用导入时也不再单独降低入口。

修复后使用提交的夹具 `compiler/graph/testdata/init/side-effect-main.ts` 与 `side-effect.ts`：

```zsh

# 输出：

# 1

# 初始化计划出现依赖边，顺序为依赖在前、入口在最后。

# order: side-effect.ts, side-effect-main.ts
# valueEdges: side-effect-main.ts -> side-effect.ts

```
