### 包装调用可核对

`go build -x` 打印的命令行显示，`compile` 与 `link` 都经过包装程序，真正的工具路径作为第一个参数传入：

```text
./bridge/go/toolexec ./.work/toolchain/.../pkg/tool/darwin_arm64/compile -o $WORK/b001/_pkg_.a -trimpath "$WORK/b001=>" -p main -lang=go1.27 …
/Users/mahoo/Projects/tynel/bridge/go/toolexec /Users/mahoo/Projects/tynel/.work/toolchain/.../pkg/tool/darwin_arm64/link -o $WORK/b001/exe/a.out -importcfg $WORK/b001/importcfg.link …
```

包装脚本只替换 `compile`，`link` 走默认分支原样转交，所以链接行为与标准工具链一致。调用契约和代价见 [bridge 说明](../reference/bridge.md)。

### 真实计算

`main.add` 的机器码只有浮点加法和返回，`main.main` 装载两个常量后调用它：

```text
TEXT main.add(SB) <autogenerated>
  <autogenerated>:1  FADDD F1, F0, F0
  <autogenerated>:1  RET

TEXT main.main(SB) <autogenerated>
  FMOVD 3280(R27), F0
  FMOVD 3272(R27), F1
  CALL main.add(SB)
  CALL main.tynelPrintFloat64(SB)
```

`FADDD` 说明加法发生在运行时，不是编译期折叠的常量；`CALL main.tynelPrintFloat64` 说明 `print` 语句接到了固定支持函数。

### 空入口是可执行函数

`bridge/go/testdata/empty.nir.json` 的 `main` 没有函数体。构建后运行，退出状态 0、无输出，说明它被建成了真实的函数而不是外部声明。

这一条最初是失败的：编译器把 `len(fn.Body) == 0` 的函数当成外部声明，链接报 `function main is undeclared in the main package`。bridge 现在给空的 `void` 函数补一条空 `return`，语义等价且能生成代码。

| 不设置 `TYNEL_NIR` 编译普通程序 | 正常构建并输出 `hello`，行为与标准编译器一致 |

错误信息按普通编译错误上报，不是内部故障（最初用 `base.Fatalf`，会打成 `internal compiler error`，已改为 `base.ErrorfAt` + `base.ExitIfErrors`）。

## 过程中确定的三条约束

1. **注入点必须在内联之后**。`inlining` 会为每个函数查找 unified IR 的函数体序列化位置，新建函数没有这份数据，早注入直接触发 `must have bodyReader` 断言。
2. **空函数体等于外部声明**。见上文，必须补隐式 `return`。
3. **构建缓存不含 bridge 身份**。Go 的缓存既不记录 NIR 内容，也不记录被 `-toolexec` 换掉的编译器；`run` 把 NIR 与编译器二进制的哈希前缀都放进 build tag，否则改完 bridge 仍会命中旧对象。这一条是在空入口用例上真实踩到的：改了 bridge 却仍报旧错误。

## 交付后的入口包装（2026-11-09）

本节记录 `entry` 字段的一次修复，执行时间是 2026-11-09 23:30 CST，代码基于提交 `da3430d` 的工作树。环境仍是 macOS 26.6.2、arm64 与锁定的 go1.27.3，夹具放在不入库的 `.work/validation/nir-entry/`。

`nir.Verify` 允许入口叫任意名字（存在、没有参数、返回 `void` 即可），但 `inject()` 只把函数逐个加入 `target.Funcs`，从不读 `m.Entry`；固定支持文件也不提供 `main`。入口不叫 `main` 时包里就没有 `main.main`，验证通过的 NIR 在链接期才失败。降低管道永远把入口命名为 `main`（`lower.EntryName`），所以这条路径只有手写 NIR 经 `build-ir` / `bridge/go/run` 才会走到。修复前基线（entry 为 `startup` 的合法 NIR）：

```text
$ ./bin/tynel build-ir .work/validation/nir-entry/startup.nir.json -o .work/validation/nir-entry/startup-app
tynel: 内部故障 (tool.failed): 外部工具执行失败：go …（退出状态 1）
  阶段: backend
  原因: # github.com/Mahoo12138/tynel/bridge/go/support
    runtime.main_main·f: function main is undeclared in the main package
$ echo $?
5
```

按选定的方案二修复：验证器保持 backend 中立，bridge 在入口不叫 `main` 时生成真正的 `main` 包装函数——没有参数、没有返回，函数体只有对 `m.Entry` 的一次调用——与用户函数一样直接建成 `ir.Func`，不生成 Go 源码。入口叫 `main` 时维持原路径，不生成包装。同时补上入口的最低限度校验（`bridge/go/run` 不经 `nir.Verify`）：`entry` 非空、指向存在的函数、没有参数且返回 `void`；包里已有 `main` 声明而入口另有其名时明确拒绝，而不是让链接器或运行时报错。修复后同一份 NIR：

```text
$ ./bin/tynel build-ir .work/validation/nir-entry/startup.nir.json -o .work/validation/nir-entry/startup-app
已生成 .work/validation/nir-entry/startup-app（2429938 字节）
$ .work/validation/nir-entry/startup-app
42
```

回归覆盖在受控驱动 `bridge/go/check`：新增 `entry.nir.json`（入口 `startup` 调用辅助函数 `answer` 并打印其返回值，输出 42）、`entry-missing.nir.json`（入口不存在，编译期拒绝）、`entry-conflict.nir.json`（NIR 里已有 `main` 函数而入口是 `startup`，编译期拒绝「无法生成入口包装」）。冲突用例能通过 `nir.Verify`——它正是验证器管不到、只有 bridge 能拒的形状；经 `build-ir` 实测它在后端阶段报 bridge 的错误，而入口缺失在验证器阶段就报 `nir.entry-missing`（退出 1）。原有 13 项用例（含 entry 为 `main` 的全部夹具与「普通构建不受影响」）没有回归。

修复前的失败基线即反向证据：同一份 NIR 在旧 bridge 下链接失败，新 bridge 下构建并运行正确。全量检查：
