## 1. 阶段目标

Stage 2 把 Tynel 从「只有 `number` / `boolean` / `void` 的编译器」推进到能承载典型 TypeScript 数据模型的编译器：

- 字符串、对象、数组和元组有明确的 Tynel 语义；
- 联合、可空值、函数值和闭包有可执行的表示；
- 泛型有明确的实现策略；
- Runtime ABI、对象布局和 GC 契约进入受控设计，而不是由 Go 的偶然实现决定。

阶段结束时不要求完整 TypeScript，也不要求类、异常、异步或 npm。目标是让常见数据处理程序可以写、可以检查、可以生成原生代码，并且每个能力都有规范入口和回归证据。

## 2. 当前基础与缺口

已经具备：

- 结构化 Facts：对象、数组、元组、函数、联合和命名类型已经能被前端描述；
- NIR schema 2：版本迁移、回放、作用域树、调试局部变量；
- `project.Resolver` 扩展点和 import 边界测试；
- 明确的源码位置映射和 NIR 回放测试。

仍然缺少：

- NIR 的类型系统只有 `number` / `bool` / `void`，没有字符串、对象、数组或联合表示；
- 能力检查仍拒绝这些类型；
- 没有堆值 ABI、对象布局、GC 可见指针约定和跨模块布局规则；
- 没有函数值、闭包和泛型的执行路径；
- 标准库还没有可以依赖的基础值类型。

## 4. 关键决策

### 4.1 字符串模型

必须在实现前决定：

- 可观察单位是 UTF-16 code unit、Unicode 码点还是 UTF-8 字节；
- `length`、索引、`slice`、相等和遍历分别使用什么单位；
- 内部存储用 UTF-8、UTF-16 还是双表示；
- 孤立代理项、非法序列和模板字符串插值的规则；
- 与 Go `string`、`[]byte` 和 Runtime 打印函数的边界。

建议优先级：先保证 JavaScript/TypeScript 开发者对 `length`、索引和 `slice` 的预期，再根据性能决定存储优化。不能直接把 Go 的 `len(string)` 当作 Tynel 字符串长度。

### 4.2 对象与结构类型

必须决定：

- 对象是静态形状布局还是字典；
- 属性偏移、可选属性、缺失属性与显式 `undefined` 如何区分；
- 对象相等是引用相等还是结构相等；
- 结构类型兼容在编译期如何判定，运行时是否需要形状信息；
- 对象字段中的指针如何对 GC 可见。

初期建议只支持静态形状对象和固定属性访问，把动态键、索引签名和字典对象留到后续。

### 4.3 数组与元组

必须决定：

- 数组是同质元素还是异质元素；
- 越界访问是返回 `undefined`、运行时报错还是编译期拒绝；
- 扩容策略、切片共享、长度和容量的语义；
- 元组是固定布局还是数组的特例；
- 数组元素指针的 GC 布局。

初期建议支持同质数组 `T[]` 和固定长度元组，越界行为在 RFC 中明确，不默认沿用 Go 的 panic。

### 4.4 联合与空值

必须决定：

- `null` 和 `undefined` 是否都是独立类型和值；
- 联合用标签联合、装箱还是其他表示；
- 判别联合和控制流缩窄的规则；
- 可选属性、可选参数和 `??` / `?.` 的运行时行为。

### 4.5 函数值与闭包

必须决定：

- 函数类型的调用约定和 ABI；
- 闭包捕获按值还是按引用，生命周期由谁管理；
- 函数值是否允许跨模块传递；
- 与 Go `func` 值的边界，不能把 Go 函数类型暴露成 Tynel API。

### 4.6 泛型

必须决定：

- 单态化、类型擦除还是字典传递；
- 约束和默认类型参数的检查规则；
- 泛型代码的编译体积和缓存策略；
- 与 Runtime ABI 和标准库的关系。

初期建议优先单态化：静态类型明确、运行时表示简单，代价是代码体积；字典传递留到有明确需求时再评估。

## 5. 推荐顺序

1. **S2.0**：先写字符串、对象/数组、联合/空值、函数和泛型五份 RFC 的最小版本，确定表示和 ABI 边界。
2. **S2.0a**：先做 NIR 类型系统扩展（schema 3）的设计，避免每加一种值类型就改一次协议。
3. **S2.1**：字符串从字面量、拼接、相等、长度开始，再加索引、切片和模板字符串。
4. **S2.2**：对象从静态形状、字面量和属性访问开始，再接结构兼容和可选属性。
5. **S2.3**：数组从字面量、索引、长度和越界开始，再做扩容、切片和元组。
6. **S2.4**：联合和空值依赖前面的值表示，放在字符串/对象/数组之后。
7. **S2.5**：函数值和闭包依赖对象/数组的布局与 GC。
8. **S2.6**：泛型依赖联合、函数值和标准库形状。
9. **S2.7**：在每个工作包中持续记录布局和 ABI，阶段末收敛成 ABI v1。

不要按「Parser 能解析」排序。每个工作包都必须同时覆盖语法、Tynel 类型规则、NIR 降低、Runtime 执行和组合回归。

## 6. 每个工作包的验收模板

- 解析成功用例和明确的拒绝用例；
- Tynel 类型正确用例、类型错误用例；
- NIR 结构、验证、序列化回放；
- 原生运行输出，包含边界值；
- 与其他已支持特性的组合用例；
- 调试段中的类型和作用域信息；
- 兼容性矩阵、语义索引和参考文档更新；
- 至少一条负向用例证明未实现写法仍在编译期被拒绝。

只有源码能编译、但无法生成可运行程序或没有运行时证据的能力，不能标记为 `supported`。

## 7. 第一刀建议

第一个可执行切片建议是 **字符串最小闭环**：

1. 写 `docs/language/semantics/strings.md` 和对应 ADR，确定可观察单位和存储策略；
2. 设计 NIR schema 3 的类型表示和字符串操作；
3. 实现字符串字面量、`+` 拼接、`===` / `!==`、`length`、`console.log(string)`；
4. 增加 ASCII、中文、emoji 和空字符串的原生回归；
5. 再扩展索引、`slice`、模板字符串和遍历。

这样可以在不引入对象、数组和 GC 复杂度的前提下，先验证「新值类型如何穿过 Facts → NIR → Runtime → 原生输出」的整条链路。对象和数组随后复用同一套类型表和 ABI 扩展点。

## 8. 明确不在本阶段

- 类、继承、访问器和装饰器；
- 异常、`try/catch`、异步和 Promise；
- npm、Node API 和完整 JavaScript 运行时；
- 动态属性、任意泛型擦除和高级类型运算；
- 完整 TypeScript 类型检查器复刻；
- 多后端和跨平台承诺。

这些能力需要单独的语义、ABI 和工具链设计，不能借 Stage 2 顺手放开。

## 9. 主要风险

- **字符串单位选择**会同时影响 API、性能和内存，必须先用 RFC 固定。
- **结构类型和对象布局**可能让编译期兼容规则与 Runtime 布局强耦合。
- **联合和可空值**会引入装箱或标签，影响所有值类型的 ABI。
- **闭包和 GC**会暴露生命周期、逃逸和写屏障问题。
- **泛型单态化**可能带来代码体积和编译时间压力。
- **Go Runtime 限制**可能迫使我们修改 Go Fork，必须把补丁和 ABI 变更记录下来。
- **过早扩大语法**会让能力检查、NIR 和 Runtime 同时失焦；每个工作包必须有独立验收。
