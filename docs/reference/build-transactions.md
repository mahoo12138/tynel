# 构建事务、并发与清理

本页说明一次 `tynel build` 或 `tynel run` 怎样把临时结果发布成最终产物：哪些文件会写、哪个时刻开始算成功、失败或中断后留下什么，以及同一输出被两个构建同时写入时会发生什么。构建身份和缓存标签见[构建身份与依赖变化](build-identity.md)，命令与退出状态见[命令行参考](cli.md)。

## 一次构建的写入顺序

```text
读取 NIR 和工具身份
  -> 放置内容寻址的 NIR 快照
  -> 取得输出锁，恢复上一次未完成的发布
  -> 后端写临时产物
  -> 发布前复核输入和工具
  -> 临时产物与临时记录一起发布
  -> 复核产物与记录，删除事务文件
```

快照和临时文件都在目标目录内，最后一步用同目录改名发布。跨文件系统改名可能失败，因此临时文件不能放在 `/tmp` 再搬到输出目录。

## 输出锁

同一输出路径只允许一个构建。锁文件是输出目录里的隐藏文件：

```text
.tynel-<输出路径绝对值的 sha256 前 12 位>.lock
```

锁用 Unix `flock` 的非阻塞独占模式。第二个构建不会排队，而是立即以环境缺失退出 4：

```text
tynel: 环境缺失 (build.output-busy): 另一个构建正在写 /…/out/app；等它结束或换一个输出路径
  阶段: build
```

锁随进程退出由操作系统释放，所以构建崩溃不会留下永久锁。锁文件本身保留，避免“删掉锁文件”和“另一个进程刚打开同名新文件”之间的竞争；它是可重建的运行时文件，不需要提交，也不要在构建进行时手工删除。不同输出路径各有自己的锁，可以并行构建。

## 临时文件与保留规则

| 路径 | 内容 | 失败或中断后 | 能否删除 |
| --- | --- | --- | --- |
| `.work/build/snapshots/<sha256>.nir.json` | 本次编译器读取的 NIR 快照，按完整内容哈希命名 | 保留；下次同内容构建复核哈希后复用 | 能；下次会重建，但不要在构建中删除 |
| `out/.tynel-build-*` | 后端正在写的临时产物 | 本次失败会删除；进程被强杀时可能残留 | 能；确认没有构建在写这个输出后删除 |
| `out/.tynel-record-*` | 已写好、尚未发布的记录 | 同上 | 能；同上 |
| `.work/build/snapshots/.tynel-tmp-*` | 原子写快照时使用的临时文件 | 进程被强杀时可能残留 | 能；确认没有构建在写后删除 |
| `out/.tynel-<hash>.pending` | 发布已开始、尚未确认完成 | 下一次同输出构建先恢复 | 不要手工删；它决定恢复方向 |
| `out/.tynel-<hash>.artifact.bak` | 上一份成功产物 | 回滚或恢复时用 | 不要手工删 |
| `out/.tynel-<hash>.record.bak` | 上一份成功记录 | 回滚或恢复时用 | 不要手工删 |
| `out/.tynel-<hash>.lock` | 输出锁 | 进程退出后锁自动释放，文件保留 | 没有构建时可以留着 |

`.work/` 下的快照是内容寻址的，删除后只会让下一次构建重新写一份；它不是业务级产物缓存，也不会读取 `.tynel/`、`.upstream/` 或 `dist/` 里的旧文件。输出目录里的 `.tynel-*` 文件只描述正在进行的发布，不属于用户程序。

## 发布和回滚

产物与记录是两个文件，文件系统没有“同时替换两个文件”的单个操作。构建采用以下顺序：

1. 先把新产物写进 `.tynel-build-*`，把新记录写进 `.tynel-record-*`，两者都刷新到磁盘。
2. 创建 `.pending`，其中记录发布开始时是否已有旧产物和旧记录。
3. 把旧产物、旧记录改名到 `.artifact.bak`、`.record.bak`。
4. 把新产物改名为目标文件，再把新记录改名为 `<产物>.build.json`。
5. 读取记录并重新哈希产物，确认 `output.sha256` 和 `output.bytes` 对得上。
6. 删除 `.pending` 和两个备份。

进程内任何一步失败都会回滚：有备份的一侧恢复备份，没有备份的一侧只删除本次已经安装的新文件。这样记录提交失败不会把旧的成功产物一起丢掉，也不会留下“新产物 + 旧记录”或“没有记录的产物”。

强杀可能停在两次改名之间。`.pending` 因此仍然存在，下一次同输出构建会先检查当前产物和记录：两者哈希一致就保留新的一对并清掉备份；不一致就按 `.pending` 里记录的旧文件状态恢复。恢复逻辑会区分“旧文件还没被移走”和“旧文件已经备份”，不会把未移动的旧记录误删。

这保证的是“未完成的发布不会被当成成功”，不是跨两个文件的绝对原子性。`.pending` 存在时，不要把目标产物和记录当作本次成功结果；下一次构建会完成恢复。构建已经开始发布后，Ctrl-C 不再中断这两次改名，避免主动制造半发布状态。

## 失败原因在哪里

发布相关错误走统一诊断，阶段通常是 `build` 或 `publish`：

| 代码 | 含义 | 退出 |
| --- | --- | --- |
| `build.output-busy` | 另一个构建持有同一输出锁 | 4 |
| `build.output-unwritable` | 输出目录、临时文件或锁文件不可写 | 4 |
| `build.record-failed` | 临时记录写不进，或记录改名失败 | 4 |
| `build.publish-pending` | 上一次发布留下无法清理的标记 | 4 |
| `build.record-mismatch` | 记录存在，但产物大小或哈希对不上 | 4 |
| `build.rollback-failed` | 发布失败后恢复旧文件也失败 | 4 |
| `build.canceled` | 调用方在发布前取消构建 | 4 |

后端的 stderr 仍保留在诊断的「原因」里，不会被改写成源码错误。失败后先看诊断，不要直接运行目标位置上遗留的文件；`run` 每次都重新构建，构建失败时不会执行旧产物。

## 取消

`tynel` 在 `main` 里安装 `SIGINT` / `SIGTERM` 处理器，把取消传给支持 `ContextRunner` 的后端执行器。后端在 `exec.CommandContext` 下运行，取消会终止子进程；构建在取得快照、启动后端、后端返回和发布前检查取消状态。取消发生在发布开始前时，临时产物被删除，旧产物和旧记录保持不变；取消发生在发布开始后时，让发布走完再返回，避免半发布。

用普通 `Runner` 的测试替身没有取消方法，构建仍会在调用前后检查 context，但无法在阻塞调用内部终止它。这一限制属于测试替身，不是真实 `Exec` 的行为。

## 同输入与工具变化

本项目没有业务级产物缓存：每次都重新载入图、检查、降低和调用后端。Go 自己的构建缓存用完整的 `identity.artifactSha256` 作为 build tag 的一部分；NIR、目标配置、`go`、修改版编译器、工具包装和支持目录的内容都进入这个标签。同一输入重复构建得到相同的身份、标签和产物哈希；记录里的开始时间和耗时仍会变化。改工具或 NIR 会换标签。

构建开始前重新读取源码依赖，发布前再次哈希 NIR 快照、`go`、修改版编译器、工具包装和支持目录。任何一项在构建期间被替换，都报 `build.input-changed`，不发布临时产物，旧产物和旧记录保持原样。

## 验证入口

- `internal/build/transaction_test.go` 覆盖锁、发布一致性、回滚、中断恢复、取消和工具变化。
- `cmd/tynel/source_test.go` 覆盖失败 `run` 不执行旧文件。
- `internal/build/identity_test.go` 覆盖输入身份、构建前后的替换和工具内容变化。
- 实际命令和哈希见[06.03 验收记录](../validation/06-03-transactions.md)。

当前只验证 `darwin/arm64`。非 Unix 平台没有实现同一输出的构建锁，`build.lock-unsupported` 会明确拒绝，而不是假装加锁成功。
