# 诊断协议

本页说明 `tynel` 怎样描述一次失败：类别与阶段分别表示什么，人类输出和机器输出如何对应，哪些内容只写到标准错误，以及每类失败是否留下产物。命令入口和退出状态见[命令行参考](cli.md)。

## 一条失败只有一个来源

源码、能力、环境、外部工具和运行错误都由 `compiler/diagnostic` 的同一份诊断描述。命令行不再为某一类错误另写一套文本；人类模式、`--diagnostics=json` 和 `check --json` 的结果都从这份描述投影出来。

一条诊断包含：

| 字段 | 含义 |
| --- | --- |
| 类别 | `source`、`usage`、`capability`、`environment` 或 `internal` |
| 代码 | 稳定标识，例如 `TS2322`、`project.missing`、`build.output-unwritable` |
| 阶段 | 失败发生在编译流程的哪一段，例如 `frontend`、`lower`、`backend` |
| 消息 | 面向人的中文说明；TypeScript 诊断保留原文 |
| 文件、行、列 | 有源码位置时填写；程序级或工具级诊断可以没有 |
| 严重程度 | TypeScript 的 `error` 或 `warning`；其他类别为空 |
| 原因 | 外部进程的 stderr、系统错误等原始内容，不做改写 |

类别决定退出状态，阶段只说明位置。一个 `frontend` 阶段的失败可以是源码错误，也可以是能力限制或环境缺失，不能把两者混成同一个数字。

## 阶段

| 阶段 | 负责的工作 |
| --- | --- |
| `cli` | 命令、选项和帮助解析 |
| `project` | 项目根、入口路径和源文件读取 |
| `graph` | 导入发现、依赖加载和环检测 |
| `modules` | 跨模块绑定、导出检查和初始化计划 |
| `frontend` | TypeScript 检查、声明事实和宿主进程 |
| `capability` | 原生子集判断 |
| `lower` | 事实降低为 NIR |
| `nir` | NIR 编码、解码与验证 |
| `build` | 构建事务、快照和输出发布 |
| `backend` | 修改版 Go 编译器的调用 |
| `publish` | 产物改名与记录写入 |
| `run` | 启动刚构建的程序 |
| `toolchain` | SDK、`go`、`compile`、`link` 等工具的定位 |
| `target` | 目标平台检查 |
| `internal` | 没有更具体阶段的内部故障 |

阶段默认从错误码前缀推导，例如 `build.*` 属于 `build`。跨进程边界时可以显式覆盖：外部编译进程失败仍记作 `backend`，不会因为错误码叫 `tool.failed` 就退回工具链阶段。

## 人类输出

默认模式把诊断写到标准错误，标准输出只留命令结果：

```text
tynel: 环境缺失 (build.output-unwritable): 无法创建输出目录 /…/blocked
  阶段: build
  原因: mkdir /…/blocked: not a directory
```

有源码位置时多一行 `位置: 文件:行:列`。TypeScript 诊断沿用一行格式：

```text
/…/math.ts:1:14: error TS2322: Type 'string' is not assignable to type 'number'.
```

这两种文本不是两套分类：前者用于编译器自己的失败，后者保留前端给出的错误码和位置。`--diagnostics=json` 会把它们投影成同一种条目。

## 机器输出

```zsh
# 全局选项可以放在命令前后；失败时标准错误只有一个 JSON 文档。
./bin/tynel --diagnostics=json check --root examples/quote main.ts
```

```json
{
  "schemaVersion": 1,
  "ok": false,
  "exitCode": 1,
  "diagnostics": [
    {
      "category": "source",
      "categoryName": "源码错误",
      "code": "TS2322",
      "stage": "frontend",
      "message": "Type 'string' is not assignable to type 'number'.",
      "severity": "error",
      "file": "/…/math.ts",
      "line": 1,
      "column": 14
    }
  ]
}
```

`category`、`stage`、`code`、`severity` 是稳定的机器字段；`categoryName` 和 `message` 是中文说明。一次失败只有一个信封，内部可以有多条源码或能力项，顺序与人类模式逐条打印的顺序相同。`ok` 由退出状态决定：只有警告时仍为 `true`，`exitCode` 为 0。

`check --json` 是命令自己的完整结果，字段形状与诊断信封不同：它的 `code` 是数字，还带字节区间、能力项和函数摘要。`--diagnostics=json` 是跨命令的失败协议。两者同时使用且检查失败时，标准输出是检查结果，标准错误是诊断信封，两路各自完整；程序的标准输出不会混入诊断。

### 输出分流

| 输出 | 内容 |
| --- | --- |
| 标准输出 | 命令结果：`check` 摘要或结果 JSON、`build` 的产物信息、`dump` 的 JSON、被运行程序自己的输出 |
| 标准错误（人类模式） | 诊断、宿主重建等进度、被运行程序自己的标准错误 |
| 标准错误（JSON 诊断模式） | 一个 JSON 诊断信封；进度被丢弃 |

`run` 在程序启动后不写编译器诊断。程序以非零状态退出时，`tynel` 原样传出该状态，不额外写信封；因此「有信封」表示编译失败，「没有信封但有非零状态」表示程序自己退出。程序自己的标准错误仍原样保留。

## 跨文件位置

入口和它显式导入的依赖都是 Tynel 读入的快照。前端返回的诊断先按文件名选择对应快照，再换算 UTF-8 字节区间为行列；依赖文件里的错误因此和入口一样有准确位置，不会被丢成零行零列。

内置声明库等没有对应快照的文件只保留路径，不硬套行列。程序级诊断也没有源码位置。依赖里的类型错误会在检查阶段结束，不会继续进入合并降低；否则同一个错误会变成 `lower.bad-type` 内部故障。失败路径上仍会尝试一次模块链接，以便优先报告带完整导出路径的 `module.*` 或 `init.*` 诊断；工具、环境和内部故障不会覆盖前端已经定位好的源码错误。

缺导出和依赖环的诊断会写出完整文件路径：

```text
tynel: 源码错误 (module.missing-export): 模块 /…/a.ts 没有导出 "nope"（被 /…/missing.ts 导入）
  阶段: modules
```

```text
tynel: 源码错误 (graph.cycle): 依赖环：/…/a.ts -> /…/b.ts -> /…/a.ts
  阶段: graph
```

## 外部进程与父进程

前端宿主是一个独立子进程。父进程按子进程的实际退出类别映射，而不是把所有非零退出都改写成环境缺失：

| 子进程情况 | 父进程处理 |
| --- | --- |
| 无法启动 | 环境缺失，原因是启动错误 |
| 启动超时或调用方给出 deadline | 环境缺失，原因保留 `deadline exceeded` |
| 以源码、用法、能力或环境状态退出 | 保留对应类别 |
| 崩溃或返回未知状态 | 内部故障，保留原始 stderr/stdout |
| 在管道模式下正常产出结果 | 解析结果，不把 stdout 当诊断文本 |

外部编译器、链接器或构建工具非零退出时按内部故障报告，并保留它的 stderr 作为「原因」；找不到工具按环境缺失报告。这样，工具崩溃、超时、缺链接器和输出目录不可写都不会伪装成用户源码的类型错误。宿主重建的进度只写到人类模式的标准错误，JSON 模式直接丢弃，避免和信封混在一起。

## 每类失败意味着什么

| 类别 | 发生了什么 | 本次是否生成产物 | 可以做什么 |
| --- | --- | --- | --- |
| `source` | 源码语法或类型不合法，或 NIR 内容无效 | 否；发布前失败，旧文件仍是旧结果 | 按文件、行、列修改源码后重跑 |
| `capability` | 写法合法但超出当前原生子集 | 否 | 改成受支持的写法；不要把它当成语法错误 |
| `environment` | 缺工具、前端源码未准备、目录不可写、目标不支持 | 否 | 按消息给出的准备命令或路径修复后重跑 |
| `internal` | 编译器或外部进程出现不该出现的故障 | 不发布；失败构建不会冒充成功 | 保留「原因」，先原样重跑；能复现再报告 |
| `usage` | 命令、选项或参数组合不对 | 否 | 用 `tynel help <命令>` 查看实际接受的参数 |

构建失败不会自动删除目标路径上已有的同名文件，也不会把它当成这次的结果。产物与记录要在成功发布后才可信；失败后应查看诊断，而不是运行遗留文件。

## 当前限制

- `tynel` 不会主动给外部工具设置统一执行超时。调用方或测试框架负责给挂起的进程设上限；已经发生的启动 deadline 会按环境缺失报告。
- 声明库里的诊断只保留路径，没有源码行列。
- 机器信封的 `schemaVersion` 目前是 1。这里描述的是当前协议；新增字段时需要同步更新本页和测试。
- 运行程序的退出状态与编译失败的 1–5 共用同一个数字空间，单看退出码不能区分二者；JSON 诊断模式是否有信封可以区分编译失败，但程序自身的标准错误不属于协议。
