# 0002 语言宪章与兼容性政策

## 背景

MVP 已完成并建立 `mvp/06-compiler-mvp` 标签，当前支持 `number`、`boolean`、`void`、函数、递归、分支、循环、局部赋值和显式相对路径模块。下一阶段要扩展字符串、对象、数组、泛型、标准库和工具链，如果继续按单个实现节点临时决定语言边界，会出现三个风险：

1. Go 后端的表示和限制被误写成 Tynel 语言语义；
2. TypeScript Parser 能解析被误写成语言已支持；
3. 上游 TypeScript 或 Go 升级后，没有统一的兼容性判断依据。

因此需要先固定语言方向、三层兼容性、状态词汇和决策流程，再开始新的语言能力实现。

## 选项

1. **只维护 MVP 操作支持表**：继续按实现节点逐项增加能力，等能力稳定后再总结语言规范。成本最低，但语言边界会长期由局部实现决定。
2. **承诺完整 TypeScript / JavaScript / Node 兼容**：以最大兼容为目标扩展。目标清晰，但类型系统、运行时、npm 生态和宿主 API 的成本远超当前项目能力，且会把「尚未实现」写成长期承诺。
3. **分层兼容 + 自有语义 + Go 基础设施**：语法长期沿用 TypeScript，类型和运行时按 Tynel 规范分阶段定义；Go 继续作为工具链和运行时基础设施，公共语言 API 由 Tynel 拥有。

## 决定

选择 3，并同时确定以下政策：

- **语法入口**：TypeScript 语法是 Tynel 的长期语言入口，不是临时迁移方案。未实现的语法必须给出稳定诊断，并在兼容性矩阵中标记状态。
- **三层兼容**：语法兼容、类型系统兼容和运行时语义兼容分别记录，不用一个「兼容 TypeScript」概括。
- **版本基线**：当前语法与诊断基线为 `typescript-go` 标签 `typescript/v7.0.2`、提交 `2bd066d8…`；Go 基线为 `go1.27.3`；唯一已验证目标为 `darwin/arm64`。
- **语义所有权**：Tynel 拥有 canonical type representation、求值顺序、值表示、模块初始化、异常、异步和内存契约的最终定义权。上游 Checker 句柄只在 facade 会话内使用，NIR 及后续阶段只消费 Tynel 自有数据。
- **Go 定位**：Go 编译器、链接器和 Runtime 是基础设施来源。Tynel 可以长期维护 Go Toolchain Fork，但不得把 `io.Reader`、`os.File`、`context.Context`、goroutine 或 channel 等 Go 概念直接暴露为 Tynel 公共 API。
- **标准库所有权**：标准库公共 API 由 Tynel 的 TypeScript 声明和语义定义，底层可以由 Tynel 代码或原生 Runtime 实现。
- **自举分层**：先实现编译器核心自举；链接器、汇编器、系统库和平台 SDK 可以继续复用 Tynel 维护的 Go Fork。
- **状态词汇**：统一使用 `supported`、`syntax-only`、`planned`、`rejected`、`deferred`、`not-targeted`，不使用含义不清的「部分支持」。
- **里程碑标记**：当前 MVP 标记为 Tynel Language Preview 0，保留原完成标签和实验历史。
- **决策流程**：影响语言语义、NIR schema、Runtime ABI、兼容性状态、版本基线或标准库公共 API 的改动，先写 ADR 或 RFC，再实现。

本决定落地为 [LANGUAGE.md](../../LANGUAGE.md)、[兼容性矩阵](../language/compatibility.md)和[语义索引](../language/semantics/README.md)。

## 影响

- 新增语言能力时，必须同时更新兼容性矩阵、语义索引、正向 / 负向 / 边界用例和验证记录；只有 Parser 通过不算完成。
- 升级 TypeScript 或 Go 基线时，先运行语法与诊断回归，再更新矩阵和锁文件。
- 代码评审需要检查「实现细节是否被误写成语言语义」，尤其是对象布局、GC 行为、调用约定和错误处理。
- 文档体系形成分层：宪章规定方向，矩阵记录状态，语义索引登记规范入口，参考文档描述当前实现，验证记录提供证据。
- 不改变现有 NIR 边界：后端仍然只能消费 Tynel 自有数据，Go 内部对象不得穿过编译器边界。

## 代价与风险

- **规范维护成本**：每项能力都需要语义文档和三层验收，短期实现速度会慢于直接放开前端白名单。
- **上游漂移**：TypeScript 和 Go 继续演进，基线升级需要额外回归；如果长期不升级，语法和生态会落后。
- **矩阵滞后**：实现先于文档更新时，矩阵可能短暂失真；通过「状态变化必须同提交更新文档」降低风险。
- **自有语义的长期负担**：字符串、对象、数组、异常和异步一旦定义，就要长期维护兼容性，不能随意更改。
- **Go Fork 维护**：补丁越多，rebase 成本越高；需要通过补丁清单和自动化回归控制。
- **过度承诺风险**：类型系统和运行时语义的分阶段目标容易被读成完整兼容；文档必须持续区分 `supported`、`rejected` 和 `planned`。

## 复评条件

出现以下情况时重新评估本决定：

- 升级 TypeScript 或 Go 基线，现基线不再能支撑语法兼容目标；
- 开始字符串、对象、数组的语义 RFC，发现三层兼容模型需要调整；
- 引入标准库公共 API 或 Native ABI，需要补充兼容性承诺；
- 开始 Go Toolchain Fork 的实质性修改，基础设施边界发生变化；
- 开始编译器自举，语言与工具链的版本模型需要重新划分；
- 发现文档状态与实际行为长期不一致，说明流程或状态词汇需要简化。
